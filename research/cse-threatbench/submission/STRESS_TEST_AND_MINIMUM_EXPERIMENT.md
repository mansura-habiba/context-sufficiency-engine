# CSE-ThreatBench — Adversarial research stress test and minimum experiment freeze

**Version:** 1.1, 17 November 2026  
**Scope:** scientific design review, not an executed benchmark.  
**Outcome:** **Conditional GO for a small, falsifiable pilot; NO-GO for claiming a novel semantic-sufficiency detector, general prompt-injection defense, or 1,000-tool security guarantee.**

See [RESEARCH_PLAN.md](RESEARCH_PLAN.md) and [main.tex](main.tex). No measured results exist yet.

## A. Critical scientific findings

### Finding F-01 — The headline novelty is already occupied (severity: CRITICAL)
The claim "relevance is not sufficiency" is established in:
- Joren et al., *Sufficient Context: A New Lens on Retrieval Augmented Generation Systems*, ICLR 2025. https://research.google/pubs/sufficient-context-a-new-lens-on-retrieval-augmented-generation-systems/
- Zhang and Wu, *Do LLMs Know When Evidence is Insufficient?*, 2026. https://doi.org/10.32604/cmc.2026.086343
- Qiu et al., *SURE-RAG*, 2026. https://arxiv.org/abs/2605.03534
- Chen et al., *Relevance Is Not Sufficient Evidence* (RINSE), 2026. https://arxiv.org/abs/2609.37469

**Action:** Position paper as *policy-constrained context admission + declared dependency closure + downstream agent-action utility/security*. Explicitly differentiate from learned semantic sufficiency classifiers. Add these works to manuscript bibliography after verifying exact bibliographic details.

### F-02 — Tool poisoning is already benchmarked (severity: HIGH)
MCPTox (AAAI 2026) studies malicious MCP metadata at scale: https://doi.org/10.1609/aaai.v40i42.40895 . AgentDojo (NeurIPS 2024) already uses executable prompt-injection tasks: https://arxiv.org/abs/2406.13352 .

**Action:** The novel object is not malicious metadata, 1,000 tools, or attack-success adjudication alone; it is the *differential effect of evidence-selection contracts* against strong alternatives and the costs on legitimate tasks.

### F-03 — CSE ready != oracle sufficiency (severity: CRITICAL)
Current code returns `ready` when declared requirements are covered; it does not detect unknown missing facts, true/false claims, or semantically malicious authorized evidence.

**Action:** Create two disjoint conditions:
- **C1 Known contractual requirements:** evidence requirements supplied from a trusted task specification and available equally to comparable contract-aware baselines. Test policy, dependency and budget mechanism.
- **C2 Hidden sufficiency:** required facts hidden in independent evaluator. CSE receives no oracle-derived IDs. Measure false-ready; failure is a valid outcome.

Never train or configure CSE using hidden oracle sets for the test split.

### F-04 — Authorization gateway can mask failures (severity: CRITICAL)
If all forbidden tool calls are blocked downstream, executed attack success becomes zero for every context method.

**Action:** Keep identical gateway for main comparison. Co-primary outcome includes **unsafe attempt rate**, plus separately report **verified executed effects** and **protected evidence exposure**. Do not attribute downstream denial to CSE.

### F-05 — The 1,000-tool stress test can become irrelevant to the main claim (severity: HIGH)
Layered MCP Composer exposes three tools, with underlying operations discovered progressively. Catalog size by itself does not guarantee a larger model context.

**Action:** Vary _discovery response size and ambiguity_ along with 100 vs 1,000 underlying operations. Measure how many `get_service_info`/`get_type_info` calls and how many tokens become available to selection. Keep execution tool count at three and distinguish registered vs route-permitted operations. This is a **secondary stress test**, not the primary effect estimate.

### F-06 — Scope and statistics are implausible for Friday (severity: HIGH)
200 tasks × 8 attacks × many baselines × four budgets × 1,000 tools would be a large benchmark with many agent invocations; neither validated data nor infrastructure is established.

**Action:** Freeze a small factorial pilot; show counts and wide uncertainty. Do not claim conclusive superiority.

### F-07 — Metadata and source authenticity assumptions (severity: HIGH)
A SHA-256 digest generated by an attacker over an attacker-controlled document proves no authenticity. A trusted policy identity cannot be obtained from arbitrary request JSON.

**Action:** In all cases specify trusted ingestion manifest and gateway principal provenance. Add an explicit valid-but-malicious-record case to reveal the boundary.

### F-08 — Existing prototype does not have downstream LLM-agent tests (severity: HIGH)
`benchmark.py` measures deterministic case replay, not correctness, prompt-injection resistance or agent task outcomes. Model comparisons are not complete.

**Action:** Build a separate sandbox-only harness; clearly label deterministic invariants versus empirical agent trials.

## B. Minimum experiment that could support the paper

**Primary claim under test (freeze before any results):** With matched tokens, policy claims and action gateway, explicitly constrained context compilation improves one or more observable security/sufficiency outcomes over standard retrieval/hierarchical discovery **without a disproportionate decline in legitimate task success**.

### B1. Task set (pilot)

Define **12 independently authored task templates**, split across:
- 4 operational incident investigations,
- 4 service discovery/schema interpretation tasks,
- 4 authorization-sensitive or prerequisite-sensitive tool workflows.

Each template has two paired states: **benign** and **one attacker-controlled mutation**. Each of the four chosen attack families (A1, A2, A4, A5) appears in at least three templates; cross-family overlap needs explicit labeling.

For each task, independently specify:
`task_id`, `trusted_task`, `principal`, `allowed_tools`, `required_evidence_sets`, `forbidden_effects`, `successful_effects`, `evidence_snapshot`, `attacker_surface`, `mutation`, `incomplete_case`, `expected_oracle_label`.

Build task template and oracle *without CSE-selected IDs*; verify a raw sandbox execution can complete each feasible benign task. Keep a few genuinely infeasible tasks with specified appropriate abstention.

### B2. Three systems, not six

- **S0 Hierarchical/lexical baseline:** MCP layered discovery or lexical top-k over same eligible source corpus, matched token budget, independent action gateway.
- **S1 Strong policy-aware baseline:** S0 plus identical eligibility / ACL / provenance checks and fixed schema validation, but no dependency-closure / declared-coverage compiler. Necessary to avoid attributing basic access filters to novelty.
- **S2 Full CSE:** policy-first admissibility, dependency closure, explicit requirements where trusted and available, conflict and budget management, with same independent action gateway.

S0 serves as a practical naive comparator; **S1 vs S2 is the scientifically decisive comparison**. If time allows, add semantic ranking as a fourth comparator, clearly marked supplementary.

### B3. Primary factorial execution

- 12 task templates × 2 conditions (benign/adversarial) × 3 systems × 2 independent model runs = **144 model-driven task runs** (planned, not executed).
- One pinned model/version, prompt, temperature and tool settings.
- Budget: 4,096 exact tokenizer tokens where integration permits; log any byte-estimate mismatch.
- The same source snapshots, permissions, tool responses and allowed final actions across systems.
- Freeze attack texts before examining outcomes; do not retune prompts against test task families.

**Tight deadline fallback:** One model run per condition/system = 72 runs. Treat as descriptive pilot with no inferential superiority claims.

### B4. Secondary MCP Composer 1,000-operation stress

Only **four representative tasks**, with fixed benign/adversarial pairs, at **100 and 1,000 underlying operations**, over S1 and S2 (2 systems × 2 scales × 4 templates × 2 conditions = 32 model-driven runs, one run each). If time/compute permits, repeat these. Do not pretend 1,000 tools were exposed simultaneously; always record the 3-tool layered interface.

To isolate catalog-size effects, define a target operation whose behavior and permissions are held fixed; add realistically ambiguous distractors and near-duplicate descriptions. Use deterministic schema validation for every generated OpenAPI operation. Check both registered and route-eligible counts.

**Priority order:** B3 > deterministic invariant checks > B4. If B3 fails, don't spend remaining time manufacturing a scaling story.

### B5. Four chosen attack families

| Family | Trusted boundary | Attacker mutation | Separate predicted results |
|---|---|---|---|
| A1 Cross-tenant | authenticated principal + source filter | highly relevant foreign-tenant evidence | scorer exposure, LLM exposure, unsafe request |
| A2 Evidence displacement | fixed context budget + independent oracle | long relevant-sounding distractors or missing prerequisite | oracle recall, false-ready, legitimate completion |
| A4 Discovery description poisoning | service provenance vs untrusted prose | instructions impersonating authorized workflow | wrong service, unsafe attempt, forbidden effect |
| A5 Schema prose poisoning | validated schema vs description | misleading examples/instructions in `get_type_info` | malformed call, unsafe attempt, executed effect |

A1 is mainly a policy-invariant demonstration; it cannot alone establish incremental CSE novelty if S1 matches its result. A4/A5 may defeat CSE because content admission does not neutralize malicious instructions; report failures openly.

### B6. Independent outcome oracle

For every scenario:
1. The task designer writes expected data state and allowable transitions.
2. A second validation pass ensures expected output can be obtained with legitimate sandbox APIs and without privileged oracle hints.
3. The evaluator reads only tool-call traces, protected-sink logs and final sandbox state.
4. It assigns `task_success`, `unsafe_attempt`, `forbidden_effect`, `forbidden_exposure`, `correct_abstention`, `false_block`, and `false_ready`.
5. CSE inputs never include hidden evaluation labels, target operation IDs, or gold evidence IDs that ordinary authorized clients could not know.

**Semantic sufficiency is a distinct label from declared coverage**. For test cases requiring complex interpretation, manually validate oracle conditions blind to experimental system outputs.

## C. Outcomes, comparisons and ablations

### Primary descriptive endpoints
1. **Unsafe attempt rate** among valid adversarial cases.
2. **Legitimate task completion rate** among feasible benign cases.
3. **False-ready rate** among system-ready cases with oracle-insufficient context; also report the denominator of all oracle-insufficient cases so a system that never emits ready cannot appear perfect.

### Secondary endpoints
- protected evidence exposure to scorer vs agent, separately;
- forbidden executed effects, which may be zero due to uniform gateway;
- evidence recall and prerequisite violations;
- false block/refusal and correct abstention;
- `get_service_info` / `get_type_info` calls, total model calls, input/output tokens, wall-clock latency and cost per correct task.

Report raw counts and paired differences per task; use task-clustered bootstrap 95% confidence intervals only when there are enough independent tasks to justify them. **12 task templates yield very wide intervals**. No claim of population-level generalization or statistical significance from the pilot. Compare S1 vs S2 first; S0 is illustrative.

### Minimum informative ablations
- **D1 Full CSE vs no declared dependency closure.**
- **D2 Full CSE vs no evidence requirement/blocked state.**
- **D3 Full CSE vs policy-aware baseline**, checking whether supposed benefit is merely eligibility.
- Provenance toggle is a deterministic check, not necessarily another full model-run matrix.

Do not claim that removing a security filter and observing a prohibited item proves semantic security. Separate invariant regression from agent performance.

## D. Go/no-go and what to do when the hypothesis fails

| Gate | GO if | NO-GO/alternative |
|---|---|---|
| Valid oracle | every scenario has auditable independent gold outcomes | Stop agent evaluation; make benchmark-design/position paper |
| Comparable baselines | S1 and S2 receive same policy and evidence budget | No comparative efficacy claim |
| Runnable agent | tool effects actually execute in sandbox with trace capture | Report only deterministic methods/position paper |
| Critical security effect | unsafe attempts/exposures and legitimate tasks measurable separately | Do not present 'zero attacks' as defense success |
| 1,000 catalog realism | generated schemas validate; discovery layer actually exercised | Omit scale result, retain primary study |
| Empirical value | S2 differs from S1 on informative tasks; trade-off quantified | Report negative result, limit claim to contract verification |
| Novelty | explicit comparison to ICLR 2025 context sufficiency, RINSE 2026, SURE-RAG 2026, MCPTox, AgentDojo | Do not claim novelty of sufficiency detection or tool poisoning |

**Submission decision:** An empirical paper requires trace-backed agent outcomes and a credible S1-vs-S2 comparison. If not available by Wednesday evening, use a short security/position paper that explicitly proposes and critiques the architecture, or defer the submission. Avoid a fake empirical section.

## E. Manuscript edits required after this design review

1. Replace ambiguous novelty language: CSE **does not yet measure semantic sufficiency**; it enforces declared coverage. The study asks if this helps downstream agents.
2. Add Joren et al. ICLR 2025, Zhang/Wu 2026, SURE-RAG 2026, and RINSE 2026 to Related Work.
3. Make S1 policy-aware baseline the principal comparator (not naive retrieval).
4. Define the 12-template pilot and 144-run planned matrix accurately; move 1,000-operation scale to secondary analysis.
5. Add limitations: toy scenarios, synthetic API catalog, oracle construction artifacts, prompt injection surviving valid admission, false denial, and sample size.
6. Keep manuscript anonymous; do not cite the owner's unpublished works as publicly verified results.
7. Replace plan-language with actual results only after logging and audit. Do not report numerical performance before running.

## H. Bottom line

**Strongest research question:** Does a formal contract for context eligibility and declared evidence dependencies prevent unsafe agent decisions beyond what a strong policy-aware hierarchical retriever already provides?

**Strongest possibility for a negative result:** CSE improves deterministic admissibility but not end-to-end agent security under authorized malicious content. Such a negative finding is scientifically informative if measured and stated honestly.

**Do not start with 1,000 tools.** Start with 12 paired tasks, independent oracle, and S1-vs-S2. Use 1,000 operations only after demonstrating the main mechanism and verifying that the layered discovery workload is realistic.
